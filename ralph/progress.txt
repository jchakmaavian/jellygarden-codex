## Codebase Patterns

READ THIS SECTION FIRST. It is the difference between a working iteration and a
wasted one.

### What this project is
Unity 6000.5.10f1, macOS. A purchased match-3 kit (Jelly Garden) carrying the
150-area King Leo story. Story layer lives in
`Assets/JellyGarden/Scripts/Story/` and has its own CLAUDE.md — read it.
Root CLAUDE.md and PLAN.md are also required reading.

### The two things that must never regress
1. **Animation, particles, VFX.** Enforced:
   `python3 tools/check_vfx_intact.py`
   It fails on a deleted/renamed visual asset, on a prefab losing a
   ParticleSystem/Animator/Animation/SpriteRenderer, and on a board script
   losing a method or shrinking. Board scripts (`LevelManager.cs`, `Item.cs`,
   `Square.cs`, `GUI/AnimationManager.cs`, `ItemAnimEvents.cs`,
   `ParticleSorting.cs`) may only be ADDED to. Mark every hook `// STORY:`.
2. **The 1209 tuned levels.** `Resources/Levels/*.txt` and
   `Resources/Targets/*.asset` are finished data. NEVER re-run
   `tools/level_gen.py` or `tools/target_gen.py`.

### Typecheck (the generated csproj does NOT see new files)
```bash
python3 tools/make_typecheck_csproj.py
dotnet build Story.Typecheck.csproj -v q --nologo     # expect 0 Error(s)
```

### Content validation
```bash
python3 tools/validate_story.py     # 150 areas / 807 tasks / 1209 stars / 1209 boards
```

### Running it (there is no browser; this is Unity)
The Unity Editor is usually already open on this project. Batchmode takes an
exclusive lock and will FAIL while it is open — do not kill the user's Editor.
Drive the open Editor instead:
```bash
osascript -e 'tell application "System Events" to tell process "Unity" to set frontmost to true'
osascript -e 'tell application "System Events" to keystroke "p" using command down'   # toggle Play
grep -E "^\[Story\]" Logs/Editor.log | tail -20
```
Screenshot the Editor with `screencapture -x -o /tmp/u.png` and crop the Game
view. Get the window rect with:
```bash
osascript -e 'tell application "System Events" to tell process "Unity" to get {position, size} of window 1'
```

### Verifying UI without clicking
Synthetic clicks on the Unity Game view are unreliable. The established pattern
is a self-driving component that runs once per play session and prints PASS/FAIL
to the log — see `Assets/JellyGarden/Scripts/Story/StoryPowerupTest.cs`. Copy
that shape for UI verification. NOTE: this project has the Input System package
as its ONLY active input handler, so `UnityEngine.Input` THROWS on read. Never
use `Input.GetKeyDown`.

### Traps that have bitten before
- `System.*` resolves into the kit's `JellyGarden.Scripts.System` namespace.
  Inside `JellyGarden.Scripts.Story` write `global::System.Random`, etc.
- `[RuntimeInitializeOnLoadMethod]` runs ONCE per domain, in the startup scene.
  Per-scene setup belongs in `StorySceneHooks.InstallForCurrentScene()`.
- The game opens on `main.unity` and loads `game.unity` afterwards. `main` has
  no `LevelManager`.
- `ItemsTypes` is a NAMESPACE-level enum, not nested in `Item`.
- Kit UI textures have their labels PAINTED INTO the artwork
  (`play_menu_01.png` says "Level"/"Target:"). Draw your own panels via
  `StoryUi` instead of reusing them.
- A ParticleSystem does NOT render inside a ScreenSpaceOverlay canvas. Use
  pooled UI quads (see `RepairVfx.cs`).

### The Royal Match reference
`docs/royal-match/` holds 11 screenshots captured off a real device plus a
README describing exactly what differs from the kit. Build against those, not
against memory. The most important findings:
- A level HUD is Target + portrait + Moves. There is NO score bar and NO star
  rating inside a level.
- A star is a currency, not a grade: one per level won, spent at 1-2 per task.
- Areas is a VERTICAL LIST of room cards, not a winding path map.
- Repairs animate on the room itself, no separate cutscene screen.

### Already done, do not redo
- One star per level: `StoryOneStar` (`StoryOneStar.Enabled`).
- Universal powerups + tap-to-fire: `Item.IsUniversalPowerup`, `Item.TapActivate`.
- Board art: `tools/item_skin_royal.py` (installed).
- Royal Match UI primitives: `StoryUi.Royal.cs` — `RoyalPanel`, `GreenButton`,
  `DoItButton`, `StarBadge`, `CreamCard`, `TopBar`. Build screens FROM these.
- A level's goal WITHOUT a board in the scene:
  `StoryLevelHud.ReadLevel(level, score)` / `StoryLevelHud.ModeOf(level)`.
  Every level carries a `Target.SCORE` entry that `CheckWinLose` enforces, so
  the score pass mark is a real goal on all 1209 levels — draw it, never hide it.

### Driving the open Editor (learned the hard way)
The Editor does NOT recompile while it is in Play mode, and a menu-triggered
editor test run during Play mode runs the STALE assembly against live play
state — which shows up as unrelated screen-test failures. Before running the
screen tests: stop Play (Cmd-P), force a refresh (Cmd-R), wait for the domain
reload, then click the menu. Check the log for the run you expect rather than
trusting the last [Story] lines.

`Logs/Editor.log` is ~3M lines and licensing errors flood the tail, so
`tail -4000 | grep` can miss the run you just did. Read the last few MB in
python and filter for lines starting `[Story]`.

Screenshots: `osascript` loses the foreground to whatever the user is doing, so
raise Unity and take the shot inside ONE osascript
(`do shell script "screencapture -x -o ..."`), not as a second Bash call.

### The branch
`ralph/royal-match-shell`, cut from `ralph/king-leo-story` — NOT from `main`.
`main` has none of the "already done" work above. Never re-cut it from `main`.

### Two shell-specific rules
- **Sample colours from `docs/royal-match/*.jpg` with PIL; never invent one.**
  The JPGs are 828x1472, the canvas reference is 1080x1920 — scale by 1.304.
- **A screen is not verified until it has been screenshotted in play mode.**
  Editor tests check strings; a rect of negative height passes every one of them
  and draws nothing. `Stretch(rect, padding)` pads all four sides — a padding
  over half the parent's height deletes the content silently.
- **Vertical metrics are fractions of the parent, not pixels.** The reference
  captures are a 9:19.5 phone; the Editor's Game view is 4:3, and a
  `ScaleWithScreenSize` canvas at match 0.5 gives it ~1663 reference units of
  height rather than 1920. A column of fixed pixel heights that fits the phone
  overlaps everywhere else, and every editor test still passes. Horizontal
  measurements stay in reference points.
- **Domain reload is off in this Editor.** Statics survive between play
  sessions, so on the second play `StorySceneHooks._subscribed` is still true
  and the story layer does nothing at all — a run that logs NOTHING is this.
  Force a real recompile between play runs by changing a character in a script;
  `touch` does not work, Unity hashes contents.
- **Give a new screen a static test seam** (`StoryLevelHud.Source`,
  `StoryLevelPopup.Launcher`): a `Func`/`Action` that is null in the game and
  swapped by a test, so the screen can be driven with no board in the scene.
- **Run editor tests through the Unity menu, not batchmode**, while the Editor
  holds the project lock. `JellyGarden > Story > Run Screen Tests` — note there
  are two top-level menus and the story's is the one WITHOUT a space. It is a
  SUB-menu: AppleScript must click `JellyGarden`, then `Story`, then the item,
  with a delay between each; addressing the leaf directly errors with -1728.
- **NEVER run the screen tests while the Editor is in Play mode.** They pass or
  fail on callbacks that only fire synchronously outside it, and the failure
  looks like a real regression in whatever you just wrote: exactly one case
  fails, *"the clue fired on the last repair"*. The tell is in the log —
  `[Story] area screen N ...` is gated on `Application.isPlaying`, so a test run
  carrying those lines was run in Play mode and is void. A good run logs
  `[Story] Area 1 (Castle Gates) restored.` before `Screen tests passed.` And
  Cmd+R DOES recompile from Play mode, so seeing your new code run proves
  nothing about it.
- **To look at a screen in Play mode use `JellyGarden > Story > Preview`**, which
  opens the area screen, grants stars and resets progress. Do not add a `// TEMP`
  early-return to a runtime script; three iterations running, one has survived
  into the next commit.
- **`interactable` is not a guard.** `onClick.Invoke()` fires on a greyed button,
  and editor tests invoke it directly. A screen that greys instead of hides must
  enforce its own rule inside the handler.
- **`rtk` collapses `grep` output to a match count.** Use `rtk proxy grep` when
  the matching lines themselves are what you need.
- **Enter play mode through `Edit > Play Mode > Play`, not Cmd+P.** The
  keystroke is silently swallowed while the Editor is compiling. The cycle that
  works: edit a character -> exit play -> focus Unity -> Cmd+R -> wait ~35s ->
  click that menu item. A run with no `[Story] Booted` line ran the old compile.
- **Read `git status` before starting.** A previous iteration may have left the
  current story built but uncommitted, and it may contain a `// TEMP` hook put
  in for a screenshot. Grep for `TEMP` before committing. This has now HAPPENED: a
  `// TEMP` `yield break` reached commit `de36cf6` and dead-coded
  `StoryPowerupTest` until US-008 removed it. Run the grep, every time.
- **Play mode cannot be detected from AppleScript.** `AXMenuItemMarkChar` of
  `Edit > Play Mode > Play` reads `missing value` in both states. Screenshot the
  toolbar and look at the Play button — blue fill means playing:
  `screencapture -x -o -R 1055,63,875,120 /tmp/toolbar.png`. Getting this wrong
  costs a void screen-test run that fails as *"the clue fired on the last
  repair"*.
- **`JellyGarden > Story > Preview` is three menu levels, not two.** Enumerate a
  menu before addressing it: `name of every menu item of menu 1 of menu item
  "Story" of menu 1 of menu bar item "JellyGarden" of menu bar 1`.
- **Prefer `Assets > Refresh` from the menu over Cmd+R** — the keystroke can be
  swallowed entirely (zero new log bytes). Confirm by watching the log grow.
- **`tail -c +N` cannot read `Logs/Editor.log`** ("illegal offset"); seek in
  python from a byte mark taken before the action.
- **An editor test that asserts a flag has not verified a layout.** `IsCovering`
  and `Aspect` are both true of a view that letterboxes anyway. Settle any
  "full-bleed / fills / centred / no bars" claim off the pixels: measure the
  painted rect in a Game-view capture and compare it to the crop the layout
  should produce, computed from the source art with PIL. Same family as the
  negative-height rect that passes every string check and draws nothing.

### Learnings for future iterations
- **The PRD's branch did not exist.** `branchName` is `ralph/royal-match-shell`;
  HEAD was `ralph/king-leo-story`. Branching from `main` as the generic Ralph
  instructions suggest would have thrown away StoryOneStar, the universal
  powerups and the Royal board skin — all listed as "already done, do not redo".
  Branched from `ralph/king-leo-story` instead. Future iterations: stay on
  `ralph/royal-match-shell`, it already carries everything.
- **Sample colours, do not guess them.** `python3 -c "from PIL import Image;
  Image.open('docs/royal-match/02-area-tasks.jpg').getpixel((x,y))"` — PIL is
  installed. The reference JPGs are 828x1472; the canvas reference resolution is
  1080x1920, so multiply coordinates by 1.304 when porting a measurement.
- **The `System.*` trap fires on `System.Collections.Generic` too.** Writing
  `System.Collections.Generic.Dictionary<,>` inline inside
  `JellyGarden.Scripts.Story` fails with
  `CS0234: 'Collections' does not exist in the namespace 'JellyGarden.Scripts.System'`.
  Put a `using System.Collections.Generic;` at the top instead of qualifying.
- **`StoryFreeGame.Enabled` is a `const bool`, so `if (Enabled) return x; return y;`
  warns CS0162 unreachable.** Use a ternary.
- **Batchmode is locked out while the Editor is open, but the menu is not.**
  This is the reliable way to run an editor test against the live Editor:
  ```bash
  osascript -e 'tell application "System Events" to tell process "Unity" to set frontmost to true'
  osascript -e 'tell application "System Events" to tell process "Unity" to click menu item "Run Screen Tests" of menu 1 of menu item "Story" of menu 1 of menu bar item "JellyGarden" of menu bar 1'
  ```
  There are TWO top-level menus, `Jelly Garden` (the kit's) and `JellyGarden`
  (the story's) — pick the one without the space. Focus first, wait ~15s for the
  recompile, then click; `Logs/Editor.log` is ~3M lines, so `tail -4000` before
  filtering for `[Story]`.
- **`grep` in this shell is proxied through `rtk` and can return "0 matches in
  0 files" for a query that plainly matches.** When a grep looks wrong, re-run
  it through a one-line python loop instead of trusting the empty result.
- Nested rounded rects, not `Outline`, for a rim: `Outline` offsets the whole
  quad and squares the corners.
- The close X is two rotated bars, not a `✕` glyph — the kit's font may not
  carry it, and a missing glyph renders as nothing at all.

## 2026-09-02 - US-002 - Level HUD: Target and Moves, no score bar

Replaced the kit's score bar with the Royal Match level HUD: a Target panel, a
portrait and a Moves panel across one blue strip.

### What was implemented
- `StoryLevelHud` — the strip, built from `StoryUi.Royal` colours and shapes.
  Target panel (icon + remaining count per target, one slot each, up to four),
  King Leo's portrait in a gold arch in the middle, Moves on the right reading
  `LevelManager.THIS.Limit`. Timed levels read "Time" and m:ss instead.
- The HUD is a child of the kit's own level canvas (`Level/Canvas/Panel`), NOT
  an overlay canvas of its own, so it inherits the kit's scaling, sort order and
  visibility. That canvas is authored at 720x1280 and the Royal metrics are in
  1080, so vertical measurements are scaled by `referenceResolution.x / 1080`
  and horizontal ones are normalised anchors.
- The kit's score bar (`BackBar`, holding the `ProgressBarScript` object), its
  star markers, its labels, `Score`, `Limit`, `TargetBlocks`, `TargetIngr` and
  `TargetScore` are deactivated — hidden, not deleted.
- `StoryLevelHud.Source` is the test seam: a `Func<HudModel>` that stands in for
  the board, so the strip can be driven with no `LevelManager` in the scene.
- `StoryScreenTests.LevelHudIsTargetAndMoves` builds the HUD, counts down a
  target and a move, checks no text on it contains "score", and logs one line.

### Verification

- `python3 tools/check_vfx_intact.py` -> "No animation, particle or VFX regressions."

### Learnings for future iterations
- **`LevelManager.THIS` is assigned in `Start`, not `Awake`.** A
  `StorySceneHooks` pass therefore sees no board, and the level UI is inactive
  until a level opens, so `GameObject.Find` on it returns null too. Anything
  needing the board must attach on `LevelManager.OnLevelLoaded` /
  `OnStartPlay` — this cost one whole play-mode cycle to find.
- **Never `SetActive(false)` the kit's `Targets` group.**
  `TargetsGroup.OnDisable` destroys the icons it made, and
  `LevelManager.CheckCollectedTarget` flies each collected piece to
  `TargetObject.guiObj` — one of those icons. Deactivating it animates to a
  destroyed transform: a VFX regression `check_vfx_intact.py` would not catch.
  Fade it with a `CanvasGroup` at alpha 0 and keep it alive.
- **`Level/Canvas/BottomPanel` draws over `Level/Canvas/Panel`.** Anything built
  under `Panel` is below the booster row no matter its sibling index, which is
  why the kit's pause button had to move INTO that row rather than be drawn over
  it. The row's own boosters supply the y to place it at.
- A screen built as a child of the kit's canvas gets visibility, scale and sort
  order for free, at the cost of one scale factor. That trade was worth it here
  and is probably right for anything else that must live inside a level.
- The Editor will not recompile while it is in Play mode, and screen tests run
  from the menu during Play mode fail for reasons that have nothing to do with
  the code. See the Codebase Patterns section.

## 2026-09-02 - US-003 - SCORE-mode levels get a visible target

Removing the score bar in US-002 left the 176 `MODE 0` levels with an icon and a
number that never moved. The Target panel now states the pass mark and how close
the player is to it.

### What was implemented
- **The finding that shaped this.** Every one of the 1209 levels carries a
  `Target.SCORE` entry in its `Targets/LevelN.asset`, with `targetCount ==
  star1`, and `LevelManager.CheckWinLose` requires `targetObject.All(Done)` —
  and the score entry's `Done()` is `Score >= star1`. So the score is not chrome
  that could be hidden on non-SCORE levels: it is a real win condition on every
  level, and the *only* one on the 176 SCORE levels.
- `StoryLevelHud` draws a score target as `have/need` ("270/300") against
  `LevelManager.star1`, clamped at the mark and green once met, instead of a
  static remaining count. The strip still never uses the word "score".
- `StoryLevelHud.ReadLevel(level, score)` — the same HudModel built from
  `Resources/Levels/N.txt` (STARS, LIMIT) plus `Resources/Targets/LevelN.asset`,
  with **no board in the scene**. `ModeOf(level)` reads the MODE line.
  US-004's level popup needs exactly this to state a level's goal; it is here
  rather than in the popup because the HUD is where the target model lives.
- `HudModel.PassMark`, `HudTarget.Text` / `IsScore` / `Display`,
  `StoryLevelHud.TargetTexts()` for tests.
- Slot counts got `resizeTextForBestFit`, so "270/300" and "4" both fit whether
  the card holds one slot or three.
- `StoryScreenTests.ScoreLevelsShowTheirPassMark` drives the HUD from the
  shipped data for one SCORE and one non-SCORE level, checks the number moves
  with the score and stops at the mark, and sweeps **all 1209 levels** for an
  empty Target panel.

### Files changed
- `Assets/JellyGarden/Scripts/Story/StoryLevelHud.cs`
- `Assets/JellyGarden/Scripts/Story/Editor/StoryScreenTests.cs`
- `Assets/JellyGarden/Scripts/Story/CLAUDE.md`

### Verification
- `dotnet build Story.Typecheck.csproj -v q --nologo` -> **0 Error(s)**
- `python3 tools/check_vfx_intact.py` -> "No animation, particle or VFX regressions."
- `python3 tools/validate_story.py` -> "All checks passed."
- JellyGarden > Story > Run Screen Tests -> **"[Story] Screen tests passed."**:
```
[Story] SCORE level 2: Target [0/300] Moves 17
[Story] non-SCORE level 1 (mode BLOCKS): Target [0/100 4] Moves 6
[Story] Target panel: 1209 levels checked, none empty.
```
- Play mode, Game-view screenshots:
  - level 2 (SCORE): Target = star icon over **270/300**, Moves 14.
  - level 1 (BLOCKS): Target = **100/100** and **2**, Moves 4.

### Learnings for future iterations
- **Read the shipped data before believing the story.** "SCORE levels have no
  target" was the premise; the assets say every level has a SCORE target and the
  win check enforces it. One `python3` sweep over
  `Resources/Levels/*.txt` + `Resources/Targets/*.asset` settled it in a minute
  and changed the design. Mode counts: 176 SCORE, 276 COLLECT, 279 INGREDIENT,
  478 BLOCKS.
- **`Targets/*.asset` uses two field names for the same field.** The kit's
  hand-authored assets say `count:`, the generated ones say `targetCount:`;
  `[FormerlySerializedAs("count")]` on `TargetObject.targetCount` reconciles
  them. A regex over the YAML must accept both or it silently finds nothing.
- **Never reorder the HUD's target slots.** `AimKitIconsAtThisHud` matches the
  kit's `TargetIcon`s to slots by index, so the model must keep
  `LevelManager.targetObject` order. The asset order genuinely varies
  (`('0','3')` on 415 levels, `('3','0')` on 63).
- **To play a specific level in the Editor**, temporarily point
  `StoryPowerupTest`'s `StoryFlow.LaunchLevel(1, 1)` at the level you want — it
  is the only thing that drives the Editor to a board on its own. Cmd-P to stop,
  patch, Cmd-R, wait ~30s for the domain reload, Cmd-P, wait ~30s, screenshot,
  then `git checkout --` the file. There is no menu item for this.
- **One osascript for focus + screencapture**, as the patterns section says, and
  crop from the full-screen shot with PIL afterwards — the Game view sits at
  roughly (1130,200)-(1510,340) in a 1920x1080 capture of this layout.
- `resizeTextForBestFit` is the cheap answer whenever one slot has to hold both
  a one-character and a seven-character number.

wants, and Play.

### Learnings for future iterations
- **Vertical metrics on a story screen must be fractions, not pixels.** This is
  the big one. The reference captures are a 9:19.5 phone; the Editor's Game
  view is 4:3. A `ScaleWithScreenSize` canvas at `matchWidthOrHeight 0.5` hands
  a 4:3 view ~1663 reference units of height rather than 1920, so a column of
  fixed pixel heights that fits the phone silently overlaps everywhere else.
  The booster row drew *underneath* the Play button while every editor test
  passed. Anchor vertical positions as fractions of the parent, keep horizontal
  measurements in reference points, and put `resizeTextForBestFit` on any text
  in a box that can shrink.
- **This Editor has Enter Play Mode with domain reload off.** Statics survive
  between play sessions, so `StorySceneHooks._subscribed` and friends stay true
  and the whole story layer — boot logs, map labels, the powerup self-test —
  silently does nothing on the second play. A play run that logs *nothing* is
  this, not a bug in the code. Force a real recompile between runs: `touch` is
  not enough, Unity hashes contents, so change a character. That, not
  patience, is what makes the screenshot cycle work.
- **Read the kit before inventing a mechanic.** "Three pre-level boosters" is
  already in `LevelManager.SetPreBoosts` and `BoostIcon.ActivateBoost`, down to
  the 5/5/1 counts and the spend. The story layer only had to carry a choice
  across a scene load.
- **Check that what a screen offers can ever be obtained.** The row was
  correct and permanently locked, because `StoryFreeGame.Grantable` listed only
  one of the three. A screen that shows a thing the game never grants is a dead
  end, and no test catches it.
- **`OnLevelLoaded` fires more than once per level** (`ReGenLevel` calls it
  twice, and again on no-more-matches). Anything applied there must clear
  itself or be idempotent.
- The kit's booster art lives outside Resources; `tools/ui_sprites.py` is the
  house way to copy a kit sprite in, `.meta` and all. Add to its `WANTED` map
  rather than hand-copying a png.
