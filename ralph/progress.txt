## Codebase Patterns

- The playtest is driven from the OPEN Editor, never batchmode: batchmode wants
  the project lock the user's Editor already holds. `King Leo > Preview >
  Playtest the band file` plays whatever level list is in
  `ralph/playtest_band.txt` and LEAVES THE EDITOR OPEN. The batchmode entry
  point (`RunHeadless`) is the one that quits the Editor when the report lands —
  never click a menu item wired to it.
- A `/` in a `[MenuItem]` path opens a SUBMENU. A menu item cannot be named
  after a file path.
- The playtest report is at
  `~/Library/Application Support/DefaultCompany/King Leo/playtest.txt`
  (`Application.persistentDataPath`; the Editor writes to the same place a
  player does). Poll for the file rather than reading the log.
- `osascript ... set frontmost to true` alone does NOT raise Unity when another
  app owns the screen. Add `perform action "AXRaise" of window 1`.
- Play mode is read off the toolbar: a BLUE button with a square is playing, a
  grey triangle is not. Capture `-R 116,30,875,90` (the Unity window rect from
  `get {position, size} of window 1`) and crop with PIL.
- Unity queues script compilation while it is in Play mode. Exit Play, then
  `Assets > Refresh`, and confirm the recompile landed by asking the menu bar
  for a name you just changed — do not trust a byte count.

- Screenshots of a playtest land in
  `~/Library/Application Support/DefaultCompany/King Leo/playtest/`, two per
  level, `0001_level_1_start.png` / `..._end.png`. A visual fault raises no
  error and ends no level: look at the PNGs, do not infer from the report.
  `WaitForEndOfFrame` never returns under `-nographics`, so any new capture
  must be gated on `SystemInfo.graphicsDeviceType != Null`.

- NEVER launch the player full screen, and never write the flags out yourself.
  `tools/run_player.sh` is the only thing that launches the game; it holds them
  (393x852, iPhone 15/16 portrait) and passes anything else through, so
  `tools/run_player.sh -storyplaytest`. `python3 tools/check_launch_args.py`
  fails on a second copy of the flags, on a file that opens the .app itself, and
  on a `ScreenCapture.CaptureScreenshot` that is not `StoryWindow.Capture`.
  Player shots are 786x1704 (393x852 at superSize 2); Editor shots are
  2160x3840, the right superSize and the WRONG aspect — measure a layout off a
  player run, never off an Editor one.

- **Rewrite `ralph/prd.json` with `ensure_ascii=False`.** Python's default
  escapes every em dash to `\u2014` and turns a two-line story update into an
  80-line diff.
- **A band of levels is one command: `python3 tools/playtest_sweep.py --levels
  1-16`.** It runs the built player in batches of 8, kills a batch that writes
  no report inside its timeout and lists it as hung, moves each batch's PNGs
  aside before the next batch renumbers them from 0001, and exits non-zero on
  any finding. Everything for a run lands in
  `~/Library/Application Support/DefaultCompany/King Leo/sweeps/<timestamp>/`.
  Its exit code is not a verdict on a band: open `<run>/shots/` and look.
- **A level is two files, and they must agree.** `Resources/Levels/<n>.txt` is
  the board and the header; `Resources/Targets/Level<n>.asset` is the goal. The
  txt's MODE only names the goal — what the game actually enforces is the asset's
  `targets` array (`TargetObject.Done()`). A level can therefore say MODE 3 and
  carry a BLOCKS target of 0 and be won without touching a block.
  `python3 tools/lint_levels.py` reads both and reports the disagreements in
  0.2s. Run it before a band sweep.
- **The goal count is spelled two ways in the shipped assets.** `targetCount`
  (2569 entries) and the pre-rename `count` (221 entries), both live because of
  `[FormerlySerializedAs]`. Anything that parses a Target asset must accept both
  or it will silently read no goal at all.
- **The kit ignores cell digits it does not know.** A cell is two digits,
  `block` then `obstacle`. `CreateSquare` branches only on 0 NONE / 1 EMPTY /
  2 BLOCK / 5 DOUBLEBLOCK, and any other first digit leaves an empty square AND
  skips `CreateObstacles` entirely; `CreateObstacles` branches only on 0 / 3
  WIREBLOCK / 4 SOLIDBLOCK / 6 UNDESTROYABLE / 7 THRIVING. Nothing throws — the
  cell just quietly loses what it was meant to hold.
- **Item colours are `Random.Range(0, colorLimit)`.** A COLLECT target whose
  `color` is >= the level's COLOR LIMIT names an item that can never spawn, so
  the level is unwinnable and the playtest just runs out of moves.

- **`open -a` cannot be waited on**, so a sweep cannot time a run out through
  it. `tools/run_player.sh --exec` runs the binary inside the bundle in the
  FOREGROUND instead, with the same flags. Launch a batch in its own session
  (`start_new_session=True`) and kill the process group — a killed Unity leaves
  children holding the project lock otherwise.

- **A `[MenuItem]` that is also a `-executeMethod` entry point must not call
  `EditorApplication.Exit`.** `JellyGarden > Story > Build macOS Player` did,
  and closed the user's Editor the moment the build succeeded. `StoryBuild` now
  routes every exit through `Finish()`, which returns unless
  `Application.isBatchMode`. Check any new menu item against this before
  clicking it — the same trap is why `StoryPlaytestRunner.RunHeadless` must
  never be wired to a menu.

- `[RuntimeInitializeOnLoadMethod]` runs ONCE per domain, in the startup scene.
  Per-scene setup belongs in `StorySceneHooks.InstallForCurrentScene()`.
- The game opens on `main.unity` and loads `game.unity` afterwards. `main` has
  no `LevelManager`.
- `ItemsTypes` is a NAMESPACE-level enum, not nested in `Item`.
- Kit UI textures have their labels PAINTED INTO the artwork
  (`play_menu_01.png` says "Level"/"Target:"). Draw your own panels via
  `StoryUi` instead of reusing them.
- A ParticleSystem does NOT render inside a ScreenSpaceOverlay canvas. Use
  pooled UI quads (see `RepairVfx.cs`).

### Driving the open Editor (learned the hard way)
The Editor does NOT recompile while it is in Play mode, and a menu-triggered
editor test run during Play mode runs the STALE assembly against live play
state — which shows up as unrelated screen-test failures. Before running the
screen tests: stop Play (Cmd-P), force a refresh (Cmd-R), wait for the domain
reload, then click the menu. Check the log for the run you expect rather than
trusting the last [Story] lines.

`Logs/Editor.log` is ~3M lines and licensing errors flood the tail, so
`tail -4000 | grep` can miss the run you just did. Read the last few MB in
python and filter for lines starting `[Story]`.

Screenshots: `osascript` loses the foreground to whatever the user is doing, so
raise Unity and take the shot inside ONE osascript
(`do shell script "screencapture -x -o ..."`), not as a second Bash call.

### Two shell-specific rules
- **Sample colours from `docs/royal-match/*.jpg` with PIL; never invent one.**
  The JPGs are 828x1472, the canvas reference is 1080x1920 — scale by 1.304.
- **A screen is not verified until it has been screenshotted in play mode.**
  Editor tests check strings; a rect of negative height passes every one of them
  and draws nothing. `Stretch(rect, padding)` pads all four sides — a padding
  over half the parent's height deletes the content silently.
- **Vertical metrics are fractions of the parent, not pixels.** The reference
  captures are a 9:19.5 phone; the Editor's Game view is 4:3, and a
  `ScaleWithScreenSize` canvas at match 0.5 gives it ~1663 reference units of
  height rather than 1920. A column of fixed pixel heights that fits the phone
  overlaps everywhere else, and every editor test still passes. Horizontal
  measurements stay in reference points.
- **Domain reload is off in this Editor.** Statics survive between play
  sessions, so on the second play `StorySceneHooks._subscribed` is still true
  and the story layer does nothing at all — a run that logs NOTHING is this.
  Force a real recompile between play runs by changing a character in a script;
  `touch` does not work, Unity hashes contents.
- **Give a new screen a static test seam** (`StoryLevelHud.Source`,
  `StoryLevelPopup.Launcher`): a `Func`/`Action` that is null in the game and
  swapped by a test, so the screen can be driven with no board in the scene.
- **Run editor tests through the Unity menu, not batchmode**, while the Editor
  holds the project lock. `JellyGarden > Story > Run Screen Tests` — note there
  are two top-level menus and the story's is the one WITHOUT a space. It is a
  SUB-menu: AppleScript must click `JellyGarden`, then `Story`, then the item,
  with a delay between each; addressing the leaf directly errors with -1728.
- **NEVER run the screen tests while the Editor is in Play mode.** They pass or
  fail on callbacks that only fire synchronously outside it, and the failure
  looks like a real regression in whatever you just wrote: exactly one case
  fails, *"the clue fired on the last repair"*. The tell is in the log —
  `[Story] area screen N ...` is gated on `Application.isPlaying`, so a test run
  carrying those lines was run in Play mode and is void. A good run logs
  `[Story] Area 1 (Castle Gates) restored.` before `Screen tests passed.` And
  Cmd+R DOES recompile from Play mode, so seeing your new code run proves
  nothing about it.
- **To look at a screen in Play mode use `JellyGarden > Story > Preview`**, which
  opens the area screen, grants stars and resets progress. Do not add a `// TEMP`
  early-return to a runtime script; three iterations running, one has survived
  into the next commit.
- **`interactable` is not a guard.** `onClick.Invoke()` fires on a greyed button,
  and editor tests invoke it directly. A screen that greys instead of hides must
  enforce its own rule inside the handler.
- **`rtk` collapses `grep` output to a match count.** Use `rtk proxy grep` when
  the matching lines themselves are what you need.
- **Enter play mode through `Edit > Play Mode > Play`, not Cmd+P.** The
  keystroke is silently swallowed while the Editor is compiling. The cycle that
  works: edit a character -> exit play -> focus Unity -> Cmd+R -> wait ~35s ->
  click that menu item. A run with no `[Story] Booted` line ran the old compile.
- **Read `git status` before starting.** A previous iteration may have left the
  current story built but uncommitted, and it may contain a `// TEMP` hook put
  in for a screenshot. Grep for `TEMP` before committing. This has now HAPPENED: a
  `// TEMP` `yield break` reached commit `de36cf6` and dead-coded
  `StoryPowerupTest` until US-008 removed it. Run the grep, every time.
- **Play mode cannot be detected from AppleScript.** `AXMenuItemMarkChar` of
  `Edit > Play Mode > Play` reads `missing value` in both states. Screenshot the
  toolbar and look at the Play button — blue fill means playing:
  `screencapture -x -o -R 1055,63,875,120 /tmp/toolbar.png`. Getting this wrong
  costs a void screen-test run that fails as *"the clue fired on the last
  repair"*.
- **`JellyGarden > Story > Preview` is three menu levels, not two.** Enumerate a
  menu before addressing it: `name of every menu item of menu 1 of menu item
  "Story" of menu 1 of menu bar item "JellyGarden" of menu bar 1`.
- **Prefer `Assets > Refresh` from the menu over Cmd+R** — the keystroke can be
  swallowed entirely (zero new log bytes). Confirm by watching the log grow.
- **`tail -c +N` cannot read `Logs/Editor.log`** ("illegal offset"); seek in
  python from a byte mark taken before the action.
- **A flat primitive is only proven against the surface it is drawn on.** A
  drawn icon whose interior colour matches the card behind it renders as an
  empty outline while every editor assertion passes — each rect is present,
  sized and coloured as asked. Same family as the negative-height rect.
- **A glyph's height comes from its parent, its width from that height.** A box
  sized as a fraction of a WIDE parent's width is near-square on a 9:19.5 phone
  and a sideways smear on the Editor's 4:3 view. Stretch it vertically and let an
  `AspectRatioFitter` in `HeightControlsWidth` set the width.
- **Hiding a component by deactivating its own GameObject stops its `Update`.**
  Turn off a child (the canvas) if the thing has to decide when to come back.
- **`StoryPowerupTest` launches level 1 every play session and never finishes
  it**, so the shell is "in a level" for the rest of the session. Use
  `JellyGarden > Story > Preview > Close The Level` before previewing a screen.
- **A best-fit `Text` wraps before it shrinks.** `resizeTextForBestFit` fits
  *wrapped* text to the rect, so a narrow rect gives two big lines overflowing
  the top rather than one small one. Give a variable-length label all the width
  it can have; the 150 area names are long.
- **An icon composed of stacked rects needs a near-square box.** Check the
  aspect the fractions actually produce on the target canvas, not the fractions.
- **A scrolling list's entries are FIXED reference points, not fractions of the
  screen.** The rule about vertical metrics inverts inside a ScrollRect: what
  must keep its proportions is the card, whose width is fixed, so its height is
  a fixed number of points and the viewport shows however many fit. A card sized
  as a fraction of the viewport changes shape with the Game view's aspect.
- **A long list must not resolve all its art at once.** `StoryArt` caches
  forever and the room paintings are ~0.5MB each; give art to the entries near
  the viewport on `ScrollRect.onValueChanged` and take it back from the rest.
- **A tinted parent does not tint the child that covers it.** A rimmed shape is
  outer image + rim + FACE, and the face is nearly all of what is seen — colour
  the face too, or a "greyed" thing stays its original colour with a grey
  hairline round it. Same family as the chest that rendered as two empty rings.
- **A constant is not a feature.** `SeparatorHeight` was declared and the
  separator was never built; every editor test passed. Only the screenshot found
  it. Grep your own new constants for a use before calling a screen done.
- **Changing a seam's default breaks the test that asserted the old one.**
  Setting `StoryNavBar.AreasDestination` from `StorySceneHooks` made "the Areas
  tab opens an area page" fail — and it failed in the AREAS test's neighbour, not
  in the new code. A test that asserts a fallback must clear the seam first.
- **Statics set by a play session survive into an editor test run.** Domain
  reload is off, so `StorySceneHooks` installing something in Play mode is still
  installed when the menu-driven tests run. Null the seam at the top of the case
  that depends on it.
- **An editor test that asserts a flag has not verified a layout.** `IsCovering`
  and `Aspect` are both true of a view that letterboxes anyway. Settle any
  "full-bleed / fills / centred / no bars" claim off the pixels: measure the
  painted rect in a Game-view capture and compare it to the crop the layout
  should produce, computed from the source art with PIL. Same family as the
  negative-height rect that passes every string check and draws nothing.
- **Before hiding anything the kit owns, find who looks it up.** The kit finds
  objects with `FindObjectOfType`, which skips inactive ones — so deactivating
  the map turns `InitScript`'s sprite lookup into a NullReferenceException and
  `LevelsMap.Reset`'s `.Max()` into an empty-sequence throw. Hide from `Update`
  (after the kit's own `Start`), and guard every story call into the thing you
  hid.
- **The kit turns its own things back on.** `LevelManager.ShowMap(true)` runs at
  the end of every level, so anything the story takes away has to be taken away
  every frame, not once.
- **Press the X, do not call `Close()`.** A test that opens a screen and closes
  it from code has not tested the way out that the player has. Expose the close
  button rather than reaching past it — `AreaScreen.CloseButton`.
- **Screens close onto whatever opened them, which is not always something.**
  The same screen is reachable from several places, so the guard against a dead
  end belongs in the close path (`StoryShell.EnsureFloor`) and must be a no-op
  when anything is open — and must not fire while a cutscene is playing.
- **A value derived from progress at BUILD time goes stale silently.** The room
  view's neglect wash was only recomputed when the view rebuilt (an area change
  and nothing else), so every repair left the room as dirty as it found it while
  every test passed. Give anything derived from progress a re-read on refresh —
  `AreaSceneView.SyncDamage`.
- **Do not draw your own copy of something the player can already see.** A
  cutscene staging its own before/after images over the live room is a separate
  screen however well it is aligned. Disable the copies and animate the live
  view; two copies of one room can only disagree.
- **Match a rect across canvases with `GetWorldCorners` +
  `RectTransformUtility.ScreenPointToLocalPointInRectangle`.** Copied anchors
  mean nothing outside their own canvas and its scaler.
- **Taking a backdrop away uncovers everything it was hiding.** The repair
  cutscene's title had always sat at the top of the screen; without its black it
  landed on the area page's coin and star counters. Re-check what was behind.
- **Anything hidden for the length of an animation needs a second way back.**
  `AreaScreen.ShowAfterRepair` is called from the cutscene's callback and from
  `AreaScreen.Open`, because finishing an area closes the screen mid-repair.
- **Drive a Play-mode action through the button, not the API behind it.**
  `Preview > Buy The Next Repair` invokes the row's real Do It; the order guard
  and the price check live in the handler, and a preview that skips them is
  previewing something the player cannot do.
- **Two numbers agreeing is only evidence when they were produced by different
  means.** `StoryContentAudit` reads what the story says areas 1-5 cost;
  `StoryShellTest` sums what the screens actually charged for them. 25 repairs
  and 29 stars from both is the assertion. One source counted twice is not.
- **A Play-mode walk must be able to dismiss every beat it provokes.**
  `ClueCard` times itself out; `DialogueSystem` never advances itself, so an arc
  scene hangs a walk forever. Press the screen's own handler
  (`Advance`) — that keeps the "no synthetic input" rule and tests the way out
  the player has.
- **Restoring a save file is not the whole of restoring a save.** Screens write
  their area back to `StoryProgress.CurrentArea` as they open, so anything that
  restores the file must also come home to `StoryProgress.CurrentArea` — not to
  `StoryHomeScreen.CurrentRoom`, which moves the bookmark it just put back.
- **`yield return` inside `try`/`finally` is legal in a C# iterator;
  `try`/`catch` is not.** That is how a coroutine guarantees it puts state back.
- **Two self-tests in one session need an explicit ordering.** Expose a
  finished-flag on the earlier one (`StoryPowerupTest.IsFinished`) and wait on
  it — and make it true when that test is not installed, so the wait is not a
  hang in a build that ships without it.
- Sorting orders in use: home 300, areas list 350, area page 400, nav bar 500,
  level popup 600, cutscenes 780.

  rather than left to say it twice.

  one reports how many moves it had made, the 200-move one reports the limit
  type and what is left of it. Both are level-named through the prefix.
- `_played` / `_won` / `_lost` counters, and a last line in the report:
  `SUMMARY: N level(s) played, W won, L lost, F finding(s), E error(s).`
  A level with no owning area is not counted as played.

**Verified by playing, not by reading:**

**Learnings for future iterations:**

## 2026-09-07 - US-003 - Playtest screenshots every level it plays

Implemented in `Assets/JellyGarden/Scripts/Story/StoryPlaytest.cs`.

- `OpenShotDir()` makes `Application.persistentDataPath/playtest/` once, and
  `Drive` prints the absolute path on its own line right after the "starting"
  line, so the report says where the pictures are without a caller guessing.
- `Shot(level, moment)` waits for `WaitForEndOfFrame`, calls
  `ScreenCapture.CaptureScreenshot`, then waits 0.6s for the async write to
  land — the same shape as `StoryDemoDriver.Shot`. Files are
  `{0:0000}_level_{1}_{2}.png`, so the directory sorts into playing order across

## 2026-09-07 - US-005 - One command sweeps a band of levels and prints the findings

`tools/playtest_sweep.py`, plus the one launcher change it needed.

- **`tools/run_player.sh --exec`** is new: same flags, but it runs the
  executable inside the bundle in the foreground rather than handing the bundle
  to `open -a`, which returns the instant the app starts and leaves nothing to
  wait on or kill. The executable is *found* inside `Contents/MacOS/` rather
  than named, because the product name has already changed once
  ("Match3 Games" -> "King Leo"). The flags stay in the one place, so

- **`tools/playtest_sweep.py`** takes `--levels` (`1-16`, `1,5,9`, `1-4,20`),
  `--batch` (default 8), `--timeout` (default 90s + 75s per level) and
  `--headless`. Per batch it deletes the stale report and shot directory, arms
  the run with `-playtestLevels=`, polls for the report, and kills the process
  group at the deadline. It prefers the built player and falls back to a
  batchmode `StoryPlaytestRunner.RunHeadless` when `Builds/Mac/KingLeo.app` is
  missing (honouring `KINGLEO_APP`, as the launcher does).
- Each run gets `sweeps/<timestamp>/` under the persistent data path, holding
  `batch_NNN.txt` (the report), `batch_NNN.log` (stdout) and `shots/` with every
  PNG prefixed `b001_`. That prefix is load-bearing: every run numbers its shots
  from 0001, so without it batch 2 lands on batch 1's filenames.
- The final block prints every `FINDING:` line grouped by level, the hung
  batches with their level numbers, the error count and both directories, and
  exits 1 if anything was found.
- `tools/README.md` gained a "Sweeping a band of levels" section and root

## 2026-09-07 - US-006
- Wrote `tools/lint_levels.py`: a static linter over all 1208 levels that reads
  each board beside its goal asset and reports the levels that contradict
  themselves. One line per problem as `<level>: <problem>`, non-zero exit when
  there is at least one, 0.15s for the whole game (`--levels 1-16` for a band,
  `--quiet` for counts only).
- Every rule is anchored to a line of the kit, not to taste. Read the kit first
  and only then wrote the checks: `ProcessGameDataFromString` (header + the two
  digits of a cell), `CreateSquare` / `CreateObstacles` (which digits are
  understood), the board build (`TargetBlocks = BLOCK + 2 * DOUBLEBLOCK`),
  `Item.GenItem` (`Random.Range(0, colorLimit)`), `TargetObject.Done()`,
  `CheckStars`, `LevelMakerEditor` (COLOR LIMIT clamped 3..6).
- It finds 37 problems in 37 levels. US-007 has to clear them:
  - 23 levels are MODE 3 with a BLOCKS target of 0 while the board carries 18 or
    176 blocks — a blocks level won without touching a block.
  - 12 levels have a COLLECT target for colour 4 where COLOR LIMIT is 4. That
    colour never spawns; the level is unwinnable and a playtest can only report
    "ran out of moves".
  - 2 levels have an INGREDIENT target of 0.
  - Nothing else fires. Sizes, star order, limits, colour limits, cell digits,
    score-vs-first-star and MODE-vs-asset are clean across the other 1171.
- Files changed: `tools/lint_levels.py` (new), `CLAUDE.md`, `tools/README.md`,
  `ralph/prd.json`, `ralph/progress.txt`.
- Checks: `lint_levels.py` self-tested against 18 synthetic levels in the
  scratchpad (one per rule, plus a clean control) — all 18 fire as intended;
  `check_vfx_intact.py` clean; `check_launch_args.py` clean;
  `validate_story.py` "All checks passed." (150/806/1208/1208);
  `dotnet build Story.Typecheck.csproj` 0 errors.
- `ralph/findings.md`: F-001..F-005 are all about what a screenshot shows (win
  popup skin, missing HUD, dark blurred room, shots taken under the tutorial
  overlay, and the rule that a report is not a verdict). None of them is inside
  a static linter, so none is ticked off this iteration. They stay OPEN.
- **Learnings for future iterations:**
  - The kit's win condition lives in the ASSET, not in the txt. `MODE` in the
    level file is a label; `CheckWinLose` only ever asks the asset's targets
    whether they are `Done()`. Any reasoning about "what is this level's goal"
    has to read `Resources/Targets/Level<n>.asset`.
  - `targetCount` and `count` are both live spellings in the shipped assets
    (`[FormerlySerializedAs]`). A parser that only knows one of them reads 221
    levels as having no goal — which is exactly the false-clean a linter must
    not produce. My first survey pass did precisely this.
  - The first `STARS` threshold and the asset's SCORE target are the same
    number twice: `CheckWinLose` compares `Score >= star1` when the moves run
    out, and the SCORE `TargetObject` holds the same pass mark. They agree on
    all 1208 today; anything that edits one has to edit the other.
  - `ProcessGameDataFromString` splits on "\n" with `RemoveEmptyEntries`, so a
    blank line in a board file is invisible to the kit. A parser that keeps
    blank lines will count them as rows and report a phantom SIZE mismatch.
  - `COLLECT COUNT` is read for EVERY mode, `COLLECT ITEMS` only for MODE 1 and
    2. So `COLLECT COUNT` being non-zero on a MODE 1 level is normal kit
    convention, not a fault — an early version of the linter flagged all 260
    collect levels because of this. Verify a rule against the shipped data
    before shipping it: 260 hits means the rule is wrong, not the data.
  - Ingredients spawn from `Item.GenItem` off the presence of an INGREDIENT
    target in the ASSET, not off `MODE 2`. So the 27 levels that are MODE 1 with
    an ingredient target in the asset really do work, and are not a fault.
  - Don't lint what you cannot anchor. `COLLECT ITEMS` vs the asset's `color`
    looked like a 45-level fault, but the `CollectItems` enum is only ever used
    for the PrePlay display and the id-to-colour mapping is a guess. Left out.
